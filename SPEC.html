Rev L
Changes from Rev K — §04's API table, so the GIT field can speak git. The note format is untouched. The field read CLEAN or DIRTY, and neither is a word git prints: --dirty is a flag, not an output. Worse, the pair could not distinguish a vault with one untracked note from a vault mid-rebase — both read DIRTY — while the data to tell them apart was already being fetched and discarded, since status() ran git status --porcelain and kept only whether the output was empty. So GET /api/tree's git envelope grows from {clean, ahead} to {branch, clean, staged, modified, untracked, ahead}, and the field is drawn the way git status --short and every shell prompt draw it: the branch, then + staged, ~ modified, ? untracked, ↑ ahead — a mark only when its count is above zero, so a clean vault on main reads MAIN. clean stays in the envelope and stays derived from the raw output rather than from the counts, so the two cannot start disagreeing silently. This rides the existing endpoint and adds no ninth, exactly as Rev H's git did; it is additive, so a client that reads only clean and ahead is unaffected, and no file in the vault changes shape. Also recorded here: the field could never say anything at all from a container until now — the image was FROM scratch and the state is derived by shelling out to git, which was documented in the status bar's own source and nowhere else. deploy/Dockerfile carries git; the published image stays scratch, because it RUNs nothing and that is what lets it build for both architectures without emulation.

Rev N
Changes from Rev M — §02b Screen 1's INDEX becomes a folder tree. No format change; the note format and the API are untouched. The pane drew one flat list sorted by path, which reads as a numbered register only while every note is one level down. Nesting has always worked underneath — measured, a note three folders deep is indexed, searched, tag-counted and resolves as a backlink, and notes/archive/018-nested.md has been in the frozen §09 fixture since P14 — so a vault with structure looked like a vault with a shuffled list, and at a thousand notes a flat list is a scroll rather than an index. It mirrors the filesystem with no special cases: notes/ is a folder like any other, folders sort before notes and each alphabetically, and a chain of folders holding a single folder compacts to one row, because indentation is the scarcest thing in a 250px rail and a level offering no choice is not worth spending it on. A folder is a nav row and takes the §02b state matrix unchanged — hover wash, inverse when active, inset dashed focus ring, ↑↓/j–k traversal — with ↵ folding rather than opening. The arrows work it the way the WAI-ARIA tree pattern says, which is worth following exactly because the argument for a tree was that people already know how one behaves: → opens a folded folder and steps into the first child of an open one, ← folds an open folder and otherwise steps out to the parent. h/l alias them as j/k already alias ↑/↓. The header's crumb carries the same trail — INDEX / NOTES / PROJECTS / APOLLO / 010 / LAUNCH PLAN — uncompacted, because a crumb answers where is this file and eliding a real folder to save characters would make that answer wrong. It is drawn in two parts: the trail gives way when the rail is narrow and the ref and title do not, since losing “somewhere under notes/…” is survivable and losing which note is open is not. Membership does not change: isListed still governs, so the agent contract, the stencils and the journal stay out. Folders draw what the index contains; they are not a decision to change what it contains. Fold state is stored in .register/config.json as collapsed, a list of full paths — the vault can express it, so hard rule 4 is satisfied, and unlike a display scale it should travel with the vault, because the folders do. The open note is revealed at render time rather than by un-collapsing, so what is stored stays what the reader chose instead of drifting every time ⌘K lands inside a folded folder.

Rev P
Changes from Rev O — §04 gains a tenth endpoint so a folder can be deleted from the app. The note format is untouched; the only new thing in a vault is a trash bucket holding a directory instead of a file. The product had no delete of any kind: DELETE /api/note existed and shipped, and the only caller in the whole client retired a conflict copy after a merge. Nothing in the palette, no key, no row affordance — so the answer to “remove this” was Finder, which is the same answer Rev O had just finished removing for media. A folder is not a thing this vault stores. GET /api/tree returns notes; every folder in the INDEX is derived from their paths, and a folder row exists exactly while a note is under it. So “delete this folder” can only mean trash every note under it, and the row disappears as a consequence rather than as an action. DELETE /api/folder/{path} is that operation, and doing it on the server rather than as a client loop over DELETE /api/note buys two things the loop cannot. One deletion is one bucket: the subtree is moved with a single rename, preserved at its original vault path exactly as a trashed note is, so it can be restored by moving one directory back — a loop claims a <stamp> per note and scatters one folder across as many buckets as it held. And it takes the non-note files with it: trash goes through resolve, which is .md-only and cannot name a PNG at all, so a loop empties a folder of its notes and leaves the images sitting in a directory the INDEX now draws as gone. That is not the read-only rule on GET /api/file being reopened — that rule exists so the vault cannot acquire a file its own tree will never show, and this removes. It is not a recursive mode on /api/note either, which would have meant weakening resolve's .md gate, the single definition the tree, the write path and the watcher share. Directories left empty are removed, innermost first, stopping at any direct child of the root so the §04 layout survives its own last note — and stopping at anything holding a file, since remove_dir refusing a non-empty directory is the guard and sweeping away somebody's leftovers is worse than an empty folder. The confirm is the palette (Screen 2), armed rather than replaced: §02b's answer to a modal elsewhere was “never a modal”, the palette is already the app's dialog and already keyboard-first, and a second surface would be a second focus model to get wrong. ⌫ on a focused INDEX row arms it against what that row names — which is how the INDEX gains a deletion with the nav row itself unchanged, so the state matrix still describes it exactly. The search box is not drawn while a deletion is armed. The query could never reach the two answers, so it was a text field on a destructive question that took typing and ignored it — and it was the only focusable thing on the surface, so removing it is what moves the keyboard onto the answers themselves. That is the model every nav row already uses: focus is the selection, the focused answer is the one ↵ gives, and it reads as chosen whether the palette was armed by a keystroke or by a click. In its place the frame states the question. The count in the confirm is what the INDEX can see; the notice afterwards reports what the server actually moved, because the two differ by precisely the files the reader was never shown, and promising a number the client cannot know would be worse than correcting the one it can.

§01Product definition

REGISTER is a keyboard-first second brain whose entire state is a folder of markdown files. A single small binary (register serve ~/vault) renders that folder as a fast, terminal-grade UI on localhost. Humans edit through the UI; agents edit the files directly; the watcher keeps both views identical within 100 ms. V1 ships five things — notes, links, tags, tasks, search — done to instrument grade; everything else is staged for later (§12), not refused.

V1 scope fence — deferred, not forbidden

The following are out of this run to keep v1 small, fast, and finishable. Each one has a designed landing path in §12 that respects the vault contract, so adding it later is expansion, not rework. Deferred ≠ declined.

  • Deferred to §12: query/table views ("databases"), kanban boards, graph view, plugin system, rich-text surface, realtime co-editing, native mobile shells, importers.
  • Deferred infrastructure: any proprietary sync service. V1 history and multi-device are git (or the user's Syncthing/Drive); richer sync is a §12 item, not a v1 dependency.
  • Permanent, by design: no accounts requirement, no telemetry, and the §02 design system. These are the identity of the product; everything else is schedule.

§02Design system · non-negotiable

No shadows, no border-radius, no gradients. Emphasis is a double rule (border + offset outline). Active state is full inverse video.

Component doctrine

  • Frame: header rail (44px) / sidebar (250px) / editor / inspector (268px) / status bar (30px), separated by 1px hairlines. Registration crosses at viewport corners.
  • Plate: the dimensions above are one plate unit. The product renders at whole multiples of it — 1× and 2× — chosen in Screen 6 and stored in .register/config.json. Whole multiples only, for the same reason the type scale exists: Departure Mono's em is exactly 11 design pixels, so an integer multiple keeps every design pixel on a whole device pixel and a fractional one does not. Every ratio in this section is preserved by construction, so 2× is this frame drawn twice as large and never a different layout. The scale is the user's choice; whether there is room for it is the canvas's, and 2× applies only where the frame still measures clean — below that the plate stays at 1× rather than losing the index and the inspector to its own breakpoints. Those breakpoints measure the frame in plate units, not raw viewport pixels.
  • Theme: boots into the OS scheme before first paint — a same-origin boot.js loaded synchronously in <head>, not inline, because the server sends a Content-Security-Policy and default-src 'self' forbids inline execution. INV is not a preview: it chooses a scheme and stores it in .register/config.json, exactly as Screen 6 does, so it survives a reload; the key is lit when the display differs from the OS. color-scheme declared per theme. Dark is tuned, not inverted: the rule is one ink, tuned per surface — a warm near-black ground (never #000), body ink demoted below full white to kill halation, hairlines dimmed, and the brightest ink (--hi) reserved for titles, active rows and emphasis. Light stays true black on white for long-form legibility. Pure #000/#fff maximum contrast is the amateur tell.
  • Motion: none. prefers-reduced-motion also stills the status LED.
  • A11y floor: visible dashed focus rings; full keyboard traversal (arrow / j-k in lists); text meets WCAG AA minimum, AAA for body — --dim is content-safe, --faint is decorative-only and never carries meaning; semantic landmarks.
  • Voice: plain, directive, instrument-voiced. "No notes match. [N] creates one." Errors state what happened and the fix; they never apologize.

HTTP/WS API (complete)

EndpointSemantics
GET /api/tree{vault, nextRef, git, notes[]}. Each note: path, ref, title, tags, mtime, size, etag. UI builds sidebar + search corpus from this plus bodies. vault is the vault's absolute path (§02b status bar); nextRef is the ref a new note must take — the server allocates it because only the server can see .register/trash/. P12: the envelope also carries git — {branch, clean, staged, modified, untracked, ahead} or null when the vault is not a repository of its own — which is what fills §02b Screen 1's GIT field. branch is null on a detached head; staged, modified and untracked are the three columns of git status --short, counted per path, so one path edited after staging counts in both of the first two. Rev L: the counts and the branch were added so the field can say what changed rather than only that something did.
GET /api/note/{path}Raw markdown + etag.
PUT /api/note/{path}Body + If-Match etag. Atomic tmp+rename. Stale etag ⇒ 409; client writes *.conflict-<ts>.md and surfaces it. Missing path ⇒ create.
DELETE /api/note/{path}Moves to .register/trash/, never hard-deletes. Rev P: a directory the move leaves empty is removed with it, so a folder the INDEX stops drawing is not still sitting in Finder — never past a direct child of the root, and never one still holding a file.
POST /api/revealOpens the vault in the OS file manager (§08 P5 — a browser cannot). Takes no parameters: the path is always the vault the server was launched with, so nothing a caller sends reaches a process. Refused with 403 unless the listener bound to loopback.
GET · PUT /api/config.register/config.json (§08 P9). The settings screen runs in a browser and .register/ is invisible to the note API by design, so §02b Screen 6 has no other way to reach the file it names. A PUT that is not JSON is a 400 — the client reads this at boot, and an unparseable config would break the next load with nothing on screen to explain it.
GET /api/file/{path}The images and PDFs a note references (Rev O). Read-only: nothing writes a non-note through the API, so the vault cannot acquire a file its own tree will never show. Every path guard the note API uses applies except the .md rule — .., absolute paths and dot-prefixed segments are refused, and a symlink out of the vault is refused rather than followed. The container is sniffed from its magic number, never from the extension in the request: png, jpeg, gif, webp, avif, pdf; anything else is a 415, which is what refuses a .md renamed .png and an HTML file. SVG is excluded deliberately. Served with an ETag and answering If-None-Match with a 304 from a stat, and capped at 16 MB — the read is not streamed, so the cap is also the allocation ceiling. This is the one route whose frame-ancestors is 'self' rather than 'none', so Screen 8 can frame a PDF and no other origin can.
DELETE /api/folder/{path}Trash a folder and everything under it, in one bucket (Rev P). The whole subtree moves with a single rename into .register/trash/<stamp>/, at its original vault path — so a folder is restored by moving one directory back, and the refs its notes used stay visible to next_ref and are never reissued. Non-note files go with it, which is the reason this is not a client loop over DELETE /api/note: that route is .md-only and would leave every image behind in a folder the INDEX draws as gone. Every path guard applies except the .md rule, so .., absolute paths, \\ and dot-prefixed segments are refused and a symlink is not followed; the vault root is refused by the rule that refuses an empty path, since a request has to name something. A path that is not a directory is a 404, distinct from “no such note” so the body says which of the two the request got wrong. Answers {notes, files, bucket} rather than 204: the client confirms against the notes the INDEX draws and cannot see the rest of the folder, so this is the only honest account of what left. Directories the move leaves empty are removed innermost-first, never past a direct child of the root and never one still holding a file.
GET · PUT · DELETE /api/fontThe BYOF licensed face (§03, §08 P9). Stored under .register/fonts/, gitignored by register init --git. The container is sniffed from its magic number, never from the filename a browser reported; anything that is not woff2/woff/otf/ttf is a 415. Served no-store: the bytes are the user's licensed property and a cache entry is a copy of them nobody chose to make.
WS /api/events{created|changed|removed, path, etag}, debounced 50 ms, coalesced. Powers live reload of agent edits.

That is the entire server surface. Refs, links, tasks, tags, search, templates — all client-side derivations of plain text, so the file format alone defines the product. The last three are the only endpoints not about the vault's notes: /api/reveal because opening a file manager is the one thing the UI genuinely cannot do for itself, and /api/config and /api/font because .register/ is deliberately invisible to the note API and §02b Screen 6 still has to read and write what lives there.

# REGISTER — agent operating manual

Read SPEC.html before any task. It is the contract.

## Commands
cargo run -- serve ./devvault      # run server against a test vault
cargo test · cargo fmt · cargo clippy -- -D warnings
cd app && pnpm dev                 # UI dev (proxies /api to :7777)
cd app && pnpm check && pnpm test && pnpm build && pnpm size

## Hard rules
1. §04 vault format is normative. Any change to it is a major
   version and needs my explicit approval first.
2. Design tokens only (§02). Never hardcode a color, font, or
   size; everything derives from app/src/styles/tokens.css.
3. Budgets are law (§06). If a change breaks a budget, shrink
   the change, not the budget.
4. Files are the truth. No databases, no localStorage, no state
   the vault cannot express. IndexedDB is forbidden.
5. All vault writes go through vault.rs atomic write + etag.
   Never write files any other way.
6. No new dependencies (crate or npm) without docs/ADRs/NNN.md
   and my approval.
7. Fonts: only OFL faces with OFL.txt beside them (§03). CI
   greps for strays.
8. Zero animations except the status LED; respect
   prefers-reduced-motion; keep focus rings visible.
9. TypeScript strict; Rust clippy clean with -D warnings.
10. A phase is done when: cargo test + fmt + clippy AND pnpm
    check + test + size are green. Then one conventional commit.
11. Version doctrine (§06): before scaffolding, verify every
    manifest pin against current stable (endoflife.date +
    official release pages) and bump the manifest if stable has
    moved. Pins live in .nvmrc / rust-toolchain.toml /
    packageManager only; the string "latest" is banned in
    Dockerfiles, workflows, and manifests; Renovate owns
    drift after P0.

## Style
Svelte 5 runes. Small modules. UI copy is plain, directive,
instrument-voiced. Rust: no unwrap() outside tests.

§12Roadmap · post-v1 expansion

This section exists so that "not in v1" can never harden into "not ever." Any feature — including everything below and things not yet imagined — may be added when it passes three gates: (1) it can be expressed without breaking the §04 vault contract, or it bumps the major version with a documented migration; (2) it fits the §06 budgets or ships as lazy-loaded / optional code; (3) it obeys the §02 design system, the one permanent constraint.
